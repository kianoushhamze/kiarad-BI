- دامنهٔ پنل: `panel.kiaradhealer.ir`؛ رکورد A آن در سرویس DNS ابر آروان تنظیم شده و `getent ahostsv4` روی Ubuntu، IP مورد انتظار VPS را برگردانده است.

## بررسی اولیهٔ دسترسی بیرونی

در بررسی اولیه، دو دستور curl به هم چسبیده بودند. درخواست اول با `Resolving timed out` پایان یافت و درخواست دوم در ویندوز شرکت نام دامنه را resolve کرد، TLS را برقرار کرد و برای `HEAD /login` پاسخ `200` گرفت. برای تکرار آزمون:

```cmd
curl.exe -Iv --connect-timeout 8 --max-time 15 https://panel.kiaradhealer.ir/login
```

**اقدام بعدی، بدون تغییر پیکربندی:** صفحه را در مرورگر ویندوز و از اینترنت سیم‌کارت موبایل با Wi‑Fi خاموش آزمایش و **متن دقیق خطا** را ثبت کنید؛ سپس ورود مجاز و API را با رعایت محرمانگی بررسی کنید. در صورت تکرار خطا، همان دستور curl مستقل را برای تفکیک DNS/TCP/TLS اجرا کنید.

راهنمای تفسیر: اگر DNS resolve نمی‌شود، رکوردها/کش resolver بررسی شوند؛ اگر TCP timeout یا connection refused است، firewall/security group پنل VPS و مسیر شبکه/اپراتور بررسی شود؛ اگر خطای TLS است، certificate chain/SNI و زمان دستگاه بررسی شود؛ اگر HTML باز می‌شود اما ورود/درخواست API شکست می‌خورد، مسیرهای Next.js `/api`، headerها و backend را جداگانه بررسی کنید. تست موفق روی خود VPS معادل تأیید بیرونی نیست.

## بررسی و بازیابی نگاشت‌های ویندوز

اگر سرویس روی `127.0.0.1` پاسخ می‌دهد ولی دامنهٔ عمومی پاسخ نمی‌دهد، در PowerShell ویندوز نام واقعی تونل و IPv4 خصوصی آن را به اسکریپت بدهید:

```powershell
.\scripts\repair_wireguard_portproxy.ps1 -TunnelName '<نام تونل>' -TunnelAddress '<IPv4 خصوصی ویندوز>'
```

خروجی برای پورت‌های `3300` و `8190` سلامت سرویس محلی، آماده‌بودن IP تونل، مطابقت نگاشت و پاسخ HTTP روی IP تونل را نشان می‌دهد. حالت پیش‌فرض فقط وضعیت را می‌خواند.

برای بازیابی، در PowerShell مدیر همان دستور را با `-Repair` اجرا کنید. اگر دست‌کم یکی از سرویس‌های محلی سالم و IP تونل غایب باشد، اسکریپت سرویس همان تونل را راه می‌اندازد و منتظر IP می‌ماند. اگر نگاشت موجود دقیقاً مطابق نگاشت مورد انتظار باشد و پورت آن روی IP تونل شنونده نداشته باشد، همان نگاشت را دوباره ثبت می‌کند. پس از بازیابی، HTTPS پنل و فروشگاه را از بیرون شبکه نیز آزمایش کنید.

در بررسی قطعی ۲۲ نوامبر، رویداد `411` ویندوز چند بار برای شروع آداپتور WireGuard با `Problem 0x1F` و `Problem Status 0xC00002F0` ثبت شد. لاگ سرویس نشان داد که WireGuard درایور موجود را پیدا می‌کرد و حدود ۱۵ ثانیه بعد، ساخت رابط شبکه شکست می‌خورد. این زمان با مهلت انتظار رابط در WireGuardNT مطابقت دارد. رویداد `410` در `08:35:49` شروع موفق آداپتور را ثبت کرد. در بررسی بعدی، فایل اجرایی و فایل تنظیمات سرویس وجود داشتند و سرویس روی شروع خودکار بود. علت داخلی خطای درایور از این رویدادها مشخص نشد. اسکریپت پس از فرمان راه‌اندازی حداکثر ۲۵ ثانیه منتظر IP می‌ماند. اگر آداپتور در دسترس نیست، مرحلهٔ شروع درایور را در رویدادهای `Microsoft-Windows-Kernel-PnP/Configuration` و لاگ WireGuard بررسی کنید و پس از بازگشت آداپتور، پاسخ هر دو پورت را دوباره بسنجید. [مهلت انتظار رابط در کد WireGuardNT](https://git.zx2c4.com/wireguard-nt/tree/api/adapter.c?id=90433bd)
