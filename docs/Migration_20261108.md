# برنامهٔ مهاجرت و وضعیت تأیید — ۸ نوامبر ۲۰۲۶

## وضعیت فعلی

سورس مرجع از سرفیس در commit `d2a5c43a10cd935bb3928b0fe6cdb38d393a5772` روی مخزن خصوصی `kianoushhamze/kiarad-BI` ثبت شده است. شاخهٔ `review/server-migration-20261108` اصلاحات این بررسی را روی همان نسخه نگه می‌دارد. ادغام PR یا خواندن مخزن به معنی استقرار روی سرفیس یا سرور نیست.

کارفرما اعمال هشت فایل اصلاحی و بکاپ آن‌ها را تأیید کرده است. روی سرفیس، مجموعهٔ عمومی ۷۱۵ تست با ۱۸۱ skip و هر ۲۲ گروه دیتابیس موفق بودند؛ این گروه‌ها با مجموعهٔ عمومی همپوشانی دارند. پس از اصلاح شش ابزار نگاشت/کاتالوگ برای حذف رمز ثابت، دوباره ۵۲۰ تست آفلاین موفق شدند. ۱۴ سناریوی فروشگاه، ۱۸۹ بررسی واحد فرانت و چهار سناریوی ورود نیز روی سرفیس موفق بودند؛ lint با کمبود حافظه متوقف شد، بنابراین TypeScript و build بعدی آن اجرا نشده‌اند.

Cloudflare و Pinggy در تست‌های شبکه تونل موفقی نساختند. Funnel فقط پیشنهاد شده و هنوز فعال یا آزمایش نشده است. IP ثابت قبلی منقضی است. این‌ها وضعیت دسترسی بیرونی‌اند و اثبات خرابی اتصال وب‌سرویس هلو نیستند.

## اصلاحات این بررسی

- `npm run build`، `npm run lint` و `npm run typecheck` از اجراکنندهٔ مشترک استفاده می‌کنند. سقف پیش‌فرض heap برابر ۲۰۴۸ مگابایت است و با `KIARAD_NODE_HEAP_MB` بین ۵۱۲ تا ۸۱۹۲ قابل تنظیم است. با کمتر از ۱۰۲۴ مگابایت رم آزاد، پیش از شروع ابزار پیام روشن داده می‌شود؛ سرویس یا برنامه‌ای خودکار بسته نمی‌شود. این حداقل، تضمین کافی‌بودن حافظه یا pagefile برای پایان build نیست.
- استقرار Docker پیش از migration و شروع برنامه، وجود جدول‌های اصلی `public.users`، `public.products` و `public.customers` را با SELECT بررسی می‌کند. دیتابیس خالی یا ناقص متوقف می‌شود و به restore نیاز دارد. این بررسی فقط وجود سه جدول را تأیید می‌کند؛ صحت داده، اسکیمای کامل و تازگی بکاپ باید جدا بررسی شوند.
- اجرای backup و restore موجود حفظ شده‌اند؛ تغییرات این نوبت هیچ دیتابیس واقعی، تنظیم شبکه یا زمان‌بندی شرکت را تغییر نداده‌اند.

## معماری پس از انتقال

| محل | مسئولیت |
|---|---|
| GitHub خصوصی | سورس، تست‌ها، lockfile و مستندات |
| سرور شرکت | نسخهٔ اجرایی مشخص، PostgreSQL اصلی و یک مجموعه sync فعال |
| سرفیس | نسخهٔ توسعه و آزمایش؛ برای استفادهٔ عادی فقط مرورگر کافی است |
| سیستم هلو | وب‌سرویس موجود روی LAN؛ دسترسی آن باید از خود سرور مقصد تست شود |

دو دیتابیس مستقل قابل‌نوشتن برای کار روزمره نگه ندارید؛ یکی مرجع اصلی باشد. پیش از cutover، sync و زمان‌بندی‌های سرفیس و سرور را فهرست کنید تا سفارش، سینک یا ارسال گزارش دو بار اجرا نشود. clone کردن GitHub دیتابیس، رسانه‌ها، مدل صوت یا وظایف زمان‌بندی‌شده را منتقل نمی‌کند.

## ترتیب کار در شرکت

۱. سیستم‌عامل سرور، RAM، فضای دیسک و runtime مناسب آن مشخص شود؛ Docker و نصب Node/Python با همان مقصد سازگار باشند. راهنمای PowerShell موجود، اثبات سازگاری Docker Desktop با هر نسخهٔ Windows Server نیست.
۲. پس از ادغام و انتخاب commit نهایی، سورس در پوشهٔ جدا روی سرور clone شود. `.env` و secrets از مسیر امن منتقل و مقادیر پیش‌فرض نمونه جایگزین شوند؛ در Git قرار نگیرند.
۳. از دیتابیس و رسانه‌ها backup تازه با checksum بگیرید. بکاپ تمرینی را روی مقصد خالی restore و داده‌های کلیدی را تطبیق دهید. فایل baseline فقط `SELECT 1` است و دیتابیس خالی را به اسکیمای کامل تبدیل نمی‌کند.
۴. مدل صوت، تصاویر و پیوست‌های خصوصی، نگاشت‌ها و تنظیمات sync منتقل شوند. تصویرهای Docker از سورس جدید build شوند؛ build روی سرور می‌تواند بار حافظه را از سرفیس بردارد.
۵. آدرس LAN وب‌سرویس هلو و احراز هویتش از خود سرور بررسی شود. اگر آدرس فعلی هلو نام تیل‌اسکیل باشد، آدرس LAN جایگزین و دسترسی فایروال از IP سرور محدود شود.
۶. بکاپ نهایی در بازهٔ توقف نوشتن گرفته شود؛ نویسنده‌ها و sync قبلی متوقف و یک‌بار روی سرور فعال شوند. دیتابیس/رسانه و سورس قدیمی برای بازگشت نگه داشته شوند.
۷. سلامت HTTP، ورود مدیر و ویزیتور، سفارش/لغو، پیش‌فاکتور، خزانه، صوت، فایل، دوربین، GPS و چاپ با دادهٔ آزمایشی بررسی شوند. تأیید فقط HTTP/200 کافی نیست.
۸. دسترسی گوشی با HTTPS تنظیم شود. برای تست Funnel، تیل‌اسکیل فقط روی سرور لازم است و کاربران لینک عمومی را با مرورگر باز می‌کنند. دسترسی خصوصی معمول تیل‌اسکیل روی گوشی با VPN دیگر ممکن است تداخل داشته باشد. مسیر پایدار دیگر، IP عمومی ثابت و دامنه و reverse proxy است. پورت‌های هلو، PostgreSQL و API داخلی عمومی نشوند.

## روش کار از این به بعد

خواندن کد، اصلاح، تست‌های قابل اجرا و ثبت تغییرات از GitHub انجام می‌شود. روی سرفیس لازم نیست سورس را دوباره ZIP کنید؛ تغییرات محلی جدید باید commit و push شوند تا قابل مشاهده باشند. پیش از pull یا تعویض شاخه، `git status` بررسی شود و تغییر محلی با reset اجباری دور ریخته نشود. merge به main همچنان deploy خودکار نیست.

## حدود تأیید

- به سرور شرکت، دیتابیس واقعی و سخت‌افزارها در این جلسه دسترسی اجرایی وجود ندارد.
- build در محیط بررسی فاقد /proc به سازگارساز موقت متریک حافظه نیاز داشته است؛ آن فایل وارد GitHub نشده و build معمول در مقصد لازم است.
- اجرای PowerShell استقرار، restore واقعی، هماهنگی رسانه‌ها با DB، شبکهٔ هلو، Funnel و تست میدانی گوشی اینجا تأیید نشده‌اند.
- حذف رمز از آخرین سورس، آن را از تاریخچهٔ Git پاک نمی‌کند. تاریخچه در این نوبت بازنویسی نشده؛ اگر رمز قدیمی هنوز معتبر است، تعویض آن باید با تنظیمات runtime و دیتابیس هماهنگ انجام شود.

نتیجه: آماده‌سازی سورس و ابزارهای مهاجرت پیش رفته است؛ اجازهٔ شروع بهره‌برداری بدون تست مقصد صادر نشده است.

## شواهد اجرای این بررسی

محیط محلی از بستهٔ سورس این گفتگو بازسازی شد؛ فایل‌های در حال تغییر و هفت فایل اصلاح‌شدهٔ اخیر از GitHub در commit مرجع خوانده و تطبیق داده شدند. این محیط، clone اجرایی سرور شرکت یا دیتابیس آن نیست.

- runner آفلاین: ۷۰۷ مورد، ۵۲۶ پاس، ۱۸۱ skip، صفر failure/error؛ ۱۴ تست زنده همچنان از زیرمجموعه خارجند. شش تست جدید کنترل دیتابیس در همین شمارش‌اند.
- کنترل دیتابیس: دیتابیس خالی، اسکیمای ناقص، SELECT پارامتری فقط‌خواندنی، خطای اتصال بدون افشای جزئیات و حدود ادعای سلامت تست شدند.
- ابزار Node: کمبود حافظه، مقادیر نامعتبر، انتخاب ابزار، خطای ایجاد child، signal، کد خروج و اجرای واقعی یک child آزمایشی با heap صریح تست شدند. هیچ سرویس واقعی متوقف نشد.
- ۱۴ سناریوی Node/HTTP فروشگاه موفق؛ lint صفر خطا و دو هشدار تصویر موجود؛ lint فایل‌های تغییرکرده بدون هشدار؛ TypeScript موفق.
- build تولیدی با سقف ۲۰۴۸MB در محیط محلی موفق شد. به علت نبود /proc همچنان از سازگارساز موقت متریک حافظه استفاده شد؛ این فایل در Git نیست.
- PowerShell و Docker واقعیِ مقصد، restore، آزمون مرورگری و سخت‌افزار در این بررسی اجرا نشدند.
