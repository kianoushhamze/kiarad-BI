# بازبینی انتقال کیاراد BI

این سند اصلاحیهٔ فایل `Kiarad-Transfer-20261113.md` است. اجرای کامل انتقال روی دو سیستم ویندوز شرکت هنوز تأیید نشده است.

## نسخهٔ مبنا

نسخهٔ بررسی‌شدهٔ main: `09ebfd544e5fbd7b1bcdce4c569a05ab406077bb`.
نسخهٔ `a106bf7386f9dff07472211bf85d52370179246d` در PR ۴ با این نسخه واگراست؛ تغییرات آن را نباید جایگزین کل main کرد. اصلاح CMS و آزمون وظایف از PR ۴ و اصلاح کاتالوگ از PR ۳ به مسیرهای نسخهٔ جدید منتقل شده‌اند. فروشگاه فعال اکنون در `site-healer/buy.html` است، نه `site/index.html`.

برای بستهٔ بعدی، SHA دقیق نسخهٔ اصلاح‌شده را ثبت کنید. در بلوک ساخت فایل انتقال، `$rev` باید همان SHA باشد. به‌جای fetch صرفاً PR ۴، شاخهٔ حاوی آن نسخه را fetch کنید و با `git cat-file -e "$rev^{commit}"` وجود نسخه را بررسی کنید. تغییرات محلی نصب قبلی را با `git status --short` ثبت و نگهداری کنید.

## مسیرهای اجرا

| کاربرد | نشانی محلی سرور |
|---|---|
| پنل و مدیریت سایت | `http://127.0.0.1:3000/login` و `/site-cms` |
| سلامت بک‌اند | `http://127.0.0.1:8000/health` |
| ویترین و فروشگاه | `http://127.0.0.1:8090/` و `/buy/` |

Compose فعلی فقط پنل و بک‌اند و دیتابیس را اجرا می‌کند. Next.js روی پورت ۳۰۰۰ مسیر فروشگاه `/buy/` ندارد. تغییر مقصد تونل داشبورد به ۳۰۰۰ به‌تنهایی فروشگاه را اجرا نمی‌کند.

روی سرور، بعد از اجرای بک‌اند و با Node.js 22، از پوشهٔ نسخهٔ جدید در یک PowerShell جدا اجرا کنید:

```powershell
$ErrorActionPreference = 'Stop'
node --version
if ($LASTEXITCODE -ne 0) { throw 'Node.js 22 is required.' }
$env:KIARAD_API_URL = 'http://127.0.0.1:8000'
$env:KIARAD_SITE_PORT = '8090'
node .\scripts\serve_kiaradhealer.mjs
if ($LASTEXITCODE -ne 0) { throw 'storefront_failed' }
```

این اجرا تا زمان باز بودن فرایند فعال است؛ پیش از بهره‌برداری، اجرای پایدار و شروع خودکار پس از راه‌اندازی ویندوز را در روش عملیاتی شرکت تنظیم و آزمایش کنید. پورت ۸۰۹۰ باید آزاد باشد. مقصد تونل فروشگاه باید ۸۰۹۰ و مقصد تونل پنل ۳۰۰۰ باشد؛ مقصدهای قبلی را ثبت کنید. سرور فروشگاه روی loopback گوش می‌دهد و Cloudflare محلی به آن متصل می‌شود.

## فایل محیطی در ساخت بسته

گزینهٔ `docker compose --env-file ...` مقادیر جایگذاری Compose را فراهم می‌کند؛ `env_file: .env` سرویس بک‌اند همچنان به فایل کنار Compose اشاره دارد. نبودن آن باعث شکست `docker compose config` می‌شود. برای بررسی یا اجرای Compose از پوشهٔ سورس استخراج‌شده، فایل runtime را امن به `.env` همان پوشه کپی کنید. این فایل را به `source.zip` یا بستهٔ اشتراکی اضافه نکنید. بررسی کنید `.dockerignore` آن را از ایمیج هم حذف کند.

این بازبینی شکست خود فرمان `compose build` را به‌علت نبود `.env` اثبات نکرده است؛ خطای قابل تکرار مربوط به اعتبارسنجی `compose config` است.

## ترتیب پذیرش

۱. از دیتابیس و رسانه‌های نصب فعلی بکاپ بگیرید و checksum را بررسی کنید. هنگام گرفتن بکاپ نهایی، نوشتن کاربران را تا تعیین نتیجهٔ انتقال متوقف کنید. `.env` و توکن‌ها جدا و امن منتقل شوند.

۲. مقصد جدید و دیتابیس خالی باشند. روی مقصد، همگام‌سازی خودکار هلو در شروع خاموش باشد؛ نسخهٔ قدیمی یا زمان‌بندی ویندوز نباید هم‌زمان روی مقصد جدید sync اجرا کند. پس از restore، بررسی دیتابیس و migrations و سلامت سرویس‌ها اجرا شوند.

۳. با حساب مدیر، تخفیف یک محصول آزمایشی را تعیین، تغییر و پاک کنید. تصویر و دستهٔ آن را بررسی کنید. با حساب ویزیتور، ویرایش CMS باید رد شود.

۴. تغییر قیمت CMS فقط دیتابیس محلی را تغییر می‌دهد؛ قیمت در خود هلو تغییر نمی‌کند. sync بعدی هلو ممکن است قیمت محلی را بازنویسی کند. در این اصلاحیه سیاست مالکیت قیمت تغییر نکرده است.

۵. فروشگاه را روی ۸۰۹۰ اجرا کنید. ورود مشتری، کاتالوگ و سفارش آزمایشی را بررسی کنید؛ شمارهٔ رسید باید در پنل مدیر دیده شود. قطع کاتالوگ نباید سبد خرید را پاک کند و سفارش در حالت قطع اتصال نباید ثبت موفق نمایش داده شود.

۶. ورود هلو، خواندن Customer، تازگی آخرین sync و تطبیق مطالبات جداگانه بررسی شوند. وضعیت واقعی دیجی‌کالا روی نسخهٔ جدید هنوز باید آزمایش شود؛ تست‌های خودکار از سرویس‌های شرکت استفاده نمی‌کنند.

۷. پس از پذیرش محلی، تونل‌ها را تغییر دهید و از دیتای موبایل HTTPS و دسترسی نقش‌ها را بررسی کنید. سپس تنها سرور منتخب برای sync خودکار فعال شود.

اگر پس از انتقال دادهٔ واقعی ثبت شده است، پیش از بازگشت ثبت را متوقف و از مقصد بکاپ بگیرید؛ بازگرداندن دیتابیس قدیمی بدون حفظ ثبت‌های جدید مجاز نیست.

## شواهد آزمون

- PostgreSQL 16 جدا: ۵ آزمون CMS، ۶ آزمون گردش کار پرسنل، ۱۷ آزمون سفارش؛ همگی موفق. داده‌ها ساختگی و شِماها موقت و مستقل بودند.
- آزمون‌های Node: کاتالوگ نامعتبر، قطع اتصال، حفظ سبد، بازیابی، حذف همهٔ اقلام حذف‌شده از کاتالوگ زنده، ثبت سفارش و جلوگیری از ثبت تکراری؛ بدون سفارش واقعی.
- CI این شاخه آزمون‌های SQL فوق و فایل‌های `tests/node/*.test.mjs` را علاوه بر بررسی‌های قبلی اجرا می‌کند.
- تست روی ویندوز شرکت، Cloudflare عمومی و اتصال زندهٔ هلو و دیجی‌کالا در این بازبینی اجرا نشده‌اند.
