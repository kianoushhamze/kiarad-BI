# بستهٔ انتقال کیاراد BI برای جمعه ۲۰ نوامبر ۲۰۲۶

این بسته برای **جایگزینی نصب موجود، پس از اجرای موازی و پذیرش** آماده شده است. سورس دقیق، شناسهٔ نسخه و checksum همراه بسته‌اند. نصب قبلی، دیتابیس قبلی و مقصد تونل را خودکار تغییر نمی‌دهد.

**بستهٔ Offline معتبرِ CI شامل سورس، ابزار و پنج ایمیج آمادهٔ Linux/amd64 است:** بک‌اند کیاراد، فرانت‌اند، PostgreSQL 16، Node 22 و Traccar 6.17.0. اگر در `release.json` مقدار `includes_images` برابر true و `payload\images.tar` موجود است، مرحلهٔ ۲ لازم نیست؛ مستقیم پس از شناسایی سراغ مرحلهٔ ۳ بروید. نسخهٔ سبک با `includes_images=false` ایمیج‌ها را در مرحلهٔ ۲ می‌سازد. ایمیج‌ها در CI ساخته و smoke test کانتینری آن‌ها با دادهٔ ساختگی بررسی می‌شود. این بسته شامل بکاپ یا اطلاعات محرمانهٔ شرکت نیست؛ payload خصوصی باید جداگانه از نصب مرجع تهیه شود.

نسخهٔ سبکِ بسته فقط سورس و ابزار دارد و `includes_images=false` است؛ برای آن مرحلهٔ ۲ ایمیج‌ها را روی دستگاه دارای اینترنت می‌سازد. **هیچ‌کدام شامل بکاپ شرکت، `.env`، توکن‌ها و مدل صوتی شرکت نیستند.** مرحلهٔ ۳ دادهٔ تازه را فقط از نصب مرجع شرکت می‌گیرد. پس از تکمیل payload، نصب مقصد بدون رجیستری انجام می‌شود.

## پیش از شروع

- ZIP را کامل از حالت فشرده خارج کنید و PowerShell را در پوشه‌ای باز کنید که `release.json` در آن است.
- مبدأ داده باید نصب دارای آخرین ثبت‌های واقعی باشد؛ آزمایشی‌بودن بخشی از سرور به معنی مرجع‌بودن دیتابیس آن نیست. مسیر `D:\project\kiaradbi` فقط مسیر ثبت‌شدهٔ سرفیس است، نه تشخیص خودکار نصب فعلی سرور.
- از PowerShell 5.1 ویندوز و Docker Desktop با موتور Linux/amd64 استفاده کنید. موتور باید پیش از اجرای اسکریپت‌ها آماده باشد. ابزارها کانتینرهای Windows را قبول نمی‌کنند. روی میزبان ساخت، اینترنت و فضای کافی برای build و آرشیو ایمیج‌ها لازم است؛ وضعیت کمبود فضای C در هنداف سابقه دارد. روی مقصد، اینترنت رجیستری و نصب Node.js میزبان لازم نیست؛ runtime فروشگاه نیز در آرشیو ایمیج‌ها صادر می‌شود.
- هیچ اسکریپتی `docker system prune`، حذف دیتابیس قبلی، reset اجباری Git یا تغییر خودکار Cloudflare انجام نمی‌دهد.
- هر مرحله که خطا داد، مرحلهٔ بعد را اجرا نکنید. پوشه و دادهٔ تلاش ناموفق را برای بررسی نگه دارید.

## ۱. شناسایی نصب موجود روی سرور و دستگاه مبدأ

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\01-Inspect-Server.ps1
```

فایل `server-inspection.json` نام کانتینرها، mount دیتابیس، پورت‌ها، فضای درایوها و وضعیت سرویس Cloudflare را نشان می‌دهد. رمز، توکن و command line سرویس‌ها در گزارش درج نمی‌شوند. روی هر دستگاه جدا اجرا کنید و گزارش آن را نگه دارید. نام کانتینر PostgreSQL و مسیر پروژهٔ مرجع را از نصب واقعی تعیین کنید. Docker ناموجود/آماده‌نبودن موتور مانع مرحلهٔ بعد است؛ آن را روی خود دستگاه رفع کنید.

## ۲. ساخت ایمیج‌ها، پیش از توقف کار شرکت

روی دستگاه دارای اینترنت، از همان پوشهٔ بسته:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\02-Build-Images.ps1
```

این فرمان از `source.zip` همین بسته، بک‌اند و فرانت‌اند را با برچسب نسخه می‌سازد؛ PostgreSQL 16 و Node 22 را نیز صادر می‌کند. خروجی در `payload\images.tar` و `payload\images.json` است. `images.json` شناسهٔ واقعی هر ایمیج، SHA نسخه و هش آرشیو را دارد. برای خروجی روی درایو دیگر، `-OutputDirectory 'D:\Kiarad-Payload-20261120'` بدهید و همین مسیر را در مرحلهٔ ۳ استفاده کنید.

این مرحله دیتابیس شرکت را نمی‌خواند. فضای آزاد را هم برای مسیر خروجی و هم دیسک Docker Desktop بررسی کنید. ایمیج قدیمیِ هنداف یا ZIP انتقال قبلی را جایگزین این خروجی نکنید.

## ۳. بکاپ نهایی، پس از توقف ثبت و زمان‌بندی‌های قدیمی

پیش از گرفتن بکاپ، ثبت کاربران را روی نصب مرجع متوقف کنید و sync هلو، دیجی‌کالا، وظایف زمان‌بندی‌شده و سایر نویسنده‌های دیتابیس را متوقف کنید. تا تعیین نتیجهٔ انتقال، دوباره ثبت را باز نکنید. متوقف‌کردن ثبت شامل توقف سفارش فروشگاه هم هست. اگر بک‌اند مبدأ کانتینری است، نام آن را از گزارش مرحلهٔ ۱ بررسی کنید؛ هیچ پروسهٔ هم‌نام دیگری را حدسی نبندید.

نمونهٔ زیر فقط وقتی مسیر و نام کانتینر با نصب مرجع شما تطبیق دارند:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\03-Capture-Data.ps1 -SourceRoot 'D:\project\kiaradbi' -PostgresContainer 'kiarad-postgres' -WritesStopped -SchedulesStopped
```

این مرحله بکاپ تازهٔ دیتابیس و رسانه، `.env` فعال، پوشهٔ `secrets` و در صورت وجود `data\speech-models` را به payload می‌آورد؛ همه را هش می‌کند. فایل‌های رسانهٔ مخفی هم پوشش دارند. تنظیمات نام دیتابیس و کاربر از کانتینر واقعی خوانده می‌شوند. PostgreSQL مبدأ جدیدتر از ۱۶ برای این بسته پذیرفته نمی‌شود.

**payload حاوی اطلاعات ورود است؛ آن را در گفتگو، GitHub یا لینک عمومی قرار ندهید.** اگر مبدأ روی دستگاه دیگری است، پوشهٔ کامل بسته و payload کامل را با روش خصوصی به سرور ببرید. اگر مرحلهٔ ۲ روی مسیر سفارشی اجرا شده، `-OutputDirectory` همان مسیر را بدهید. دیتابیس و توکنِ نصب آزمایشی را با دادهٔ مرجع مخلوط نکنید.

## ۴. نصب موازی روی سرور، بدون بازنویسی نسخهٔ قبلی

روی سرور، از پوشهٔ همین بسته:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\04-Install-Stage.ps1 -Destination "$env:USERPROFILE\kiarad-stage-20261120"
```

مقصد باید وجود نداشته باشد. نام پروژهٔ پیش‌فرض `kiaradstage20261120` است؛ کانتینر و volume قبلی با این نام نیز باید وجود نداشته باشند. پورت‌های **۳۳۰۰، ۸۸۰۰ و ۸۱۹۰** باید آزاد باشند. نصب از ایمیج‌های صادرشده، بدون build و pull انجام می‌شود؛ دیتابیس جدید volume جدا دارد و PostgreSQL آن روی میزبان پورت عمومی ندارد.

- پنل: `http://127.0.0.1:3300/login`
- بک‌اند: `http://127.0.0.1:8800/health`
- فروشگاه: `http://127.0.0.1:8190/buy/`

وب‌سرویس هلو طبق فایل انتقال قبلی روی `http://192.168.1.2:8080/TncHoloo/api` تنظیم می‌شود. اگر نشانی واقعی شرکت فرق دارد، `-HolooUrl` را صریح بدهید. sync هلو و اتوماسیون دستیار در مقصد خاموش‌اند. موفقیت این مرحله فقط آماده‌شدن نسخهٔ موازی است؛ `install-receipt.json` انتشار نهایی را تأیید نمی‌کند.

## ۵. آزمون فنی و پذیرش شرکت

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\05-Check-Stage.ps1 -Destination "$env:USERPROFILE\kiarad-stage-20261120" -CheckHoloo
```

این اسکریپت سلامت، عبور API از پنل، فروشگاه و ورود هلو را بررسی و `stage-checks.json` تولید می‌کند. سپس موارد زیر را با مدیر و حساب ویزیتور انجام دهید:

- ورود هر دو نقش؛ ویزیتور به مدیریت سایت و دادهٔ همکار دسترسی نداشته باشد. یک وظیفهٔ آزمایشی به شخص درست اختصاص دهید و همان را با حساب او ببینید.
- تعداد محصولات، تصاویر، قیمت و پاک‌کردن تخفیف؛ سفارش آزمایشی و مشاهدهٔ **همان شمارهٔ رسید** در پنل. این سفارش روی دیتابیس مقصد ثبت می‌شود. اگر کالا به سکوهای خارجی نگاشت فعال دارد، سفارش می‌تواند انتشار موجودی را نیز تحریک کند؛ برای آزمون از کالای آزمایشی بدون نگاشت فعال استفاده کنید.
- گزارش بدهکاران، واحد ریال/تومان، تاریخ منبع و آخرین همگام‌سازی را با هلو تطبیق دهید. ورود موفق هلو، اثبات تازگی دادهٔ مالی نیست.
- اتصال و نگاشت‌های دیجی‌کالا را بررسی کنید؛ ایجاد کالای جدید از API در کد هنوز endpoint تأییدشده ندارد. سفارش واقعی یا تغییر قیمت/موجودی سکو را بدون پذیرش کسب‌وکار انجام ندهید.
- در صورت نیاز شرکت، مدل صوت، میکروفون، موقعیت، اعلان و چیدمان را با گوشی واقعی تست کنید. آزمون دادهٔ ساختگی جای سخت‌افزار واقعی را نمی‌گیرد. تأیید حقوق نیازمند قواعد و انتساب مالی مصوب است.

## ۶. تعویض مسیر عمومی و فعال‌سازی تنها سرور نویسنده

مقصد قبلی هر hostname تونل را ثبت کنید. پس از پذیرش، مقصد hostname پنل را به `http://127.0.0.1:3300` و hostname فروشگاه را به `http://127.0.0.1:8190` تغییر دهید. دامنهٔ قطعی از هنداف قابل تأیید نبود؛ رکورد تازه‌ای را حدسی نسازید. از اینترنت موبایل، HTTPS و ورود و دسترسی نقش‌ها را آزمایش کنید. پورت‌های مبدأ قدیمی برای rollback حفظ می‌شوند.

پس از پذیرش شرکت و اطمینان از خاموش‌بودن همهٔ schedulerهای نصب‌های قدیمی:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\06-Enable-Sync.ps1 -Destination "$env:USERPROFILE\kiarad-stage-20261120" -CompanyAcceptancePassed -OldSchedulersStopped
```

این فرمان فقط همگام‌سازی خودکار هلو را روی مقصد فعال می‌کند. اتوماسیون دستیار به‌صورت پیش‌فرض خاموش می‌ماند؛ برای بازگرداندن برنامه‌های مصوب آن، `-EnableAssistantAutomations` را صریح اضافه کنید. نتیجهٔ نهایی sync و تطبیق داده‌ها را کنترل کنید و بعد ثبت کاربران را روی نسخهٔ جدید باز کنید. زمان‌بندی‌های قدیمی که مسیر یا پورت ثابت دارند باید پیش از استفادهٔ مجدد به نصب تازه منتقل و بررسی شوند؛ صرفاً دوباره روشنشان نکنید.

## بازگشت

پیش از ثبت جدید در مقصد: مقصد تونل را به نشانی ثبت‌شدهٔ قبلی برگردانید و فقط نصب قبلی را نویسنده کنید. کانتینرها و volume مرحلهٔ آزمایشی را برای بررسی حفظ کنید.

پس از هر ثبت واقعی در مقصد: ابتدا ثبت و schedulerها را متوقف کنید؛ با `scripts\backup_release.ps1` نسخهٔ جدید و نام واقعی کانتینر PostgreSQL همان پروژه، از مقصد بکاپ بگیرید. سفارش، وظیفه و سایر ثبت‌های تازه را پیش از بازگشت حفظ و تطبیق دهید. بازگرداندن بی‌بررسی دیتابیس قدیمی، ثبت‌های جدید را از بین می‌برد. ابزارهای این بسته دیتابیس موجود را بازنویسی نمی‌کنند.

`Software_Finalization_20261114.md` مرجع تغییرات جدید است. پس از ادغامPR۱۳، تنها بستهٔ ساخته‌شده ازmainنهایی و همانrunتحویل می‌شود؛ بستهٔ قبلی شامل اصلاحات تازهٔ سکوها، سفارش وGPSنیست. `source_commit`، `ci.json` و checksumهمانبسته را بررسی کنید. پذیرش عملیاتی شرکت از این کار جداست.

## حدود تأیید این تحویل

گزارش `General_Debug_20261112.md` و شواهد داخل `validation` را بخوانید. آزمون‌های Linux، PostgreSQL 16 و دادهٔ ساختگی در CI اجرا شده‌اند. CI ویندوزی PR شمارهٔ ۱۳ نیز با Windows PowerShell `5.1.20348.5773` هر ۴۵ فایل PowerShell را parse کرده، بستهٔ fixture را ساخته و چهار guard انتقال را با موفقیت گذرانده است. این تست، Docker Desktop ویندوز، بکاپ/restore واقعی روی نصب شرکت یا اتصال‌های شرکت را تأیید نمی‌کند؛ آن‌ها همچنان باید در مقصد و با دادهٔ پشتیبان‌گیری‌شده پذیرفته شوند. هیچ داده یا تنظیم سرور شرکت در این جلسه تغییر نکرده است.
